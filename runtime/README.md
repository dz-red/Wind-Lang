# WGC — сборщик мусора Wind

`wind_gc_alloc` добавляет выделение в связный список, а `wind_gc_destroy`
освобождает весь список. `wind_gc_collect` принимает корни явно и запускает
ручной mark-and-sweep. Скомпилированные программы на Linux используют WGC
по умолчанию. `./wind --boehm file.wnd` оставлен для сравнения и отката.

Чтобы прочитать код по порядку, начни с `WindGcBlock` в `gc.c`: `data` указывает
на память для программы, `next` — на следующую запись в списке. В `wind_gc_destroy`
голова списка передвигается **до** освобождения записи: после `free` читать
из неё `next` уже нельзя.

## Как работает сборка

1. `mark` находит блок по адресу и ставит метку. Если у блока есть функция
   `trace`, сборщик кладёт его на стек обхода (отдельно память не выделяет).
2. `trace` передаёт ссылки объекта в `visit`. Уже помеченные блоки не
   добавляются повторно, поэтому обход останавливается и на циклах. У простых
   блоков, например буфера строки, нет `trace`: в них не ищем ссылки.
3. Проход по списку удаляет блоки без метки и сбрасывает метки у выживших.
   `link` указывает не на блок, а на указатель, который ведёт к нему:
   это `head` или поле `next` предыдущего блока. Поэтому удаление головы
   и удаление из середины выполняются одинаково.

Блоки индексируются по адресу. Сборка начинается на безопасной границе
после того, как набралось достаточно новых блоков; порог растёт вместе с
числом живых объектов. `WGC_STRESS=1` включает сборку в каждой доступной
точке. Стек C не сканируется.

Проверка из корня репозитория (без Boehm GC):

```sh
gcc -std=c11 -Wall -Wextra -Werror runtime/gc.c tests/gc-heap.c -o /tmp/wind-gc-heap-test
/tmp/wind-gc-heap-test
```

## Использование

```sh
make
./wind -s examples/gc-strings.wnd
sh tests/gc-strings.sh
```

Для обычной сборки на Linux Boehm GC не нужен. GCC компилирует
`output_ast.c` и файлы рантайма отдельно.
Для этого оставь папку `runtime/` на месте: `make` записывает её путь в
компилятор. Создаваемые во время работы строки (склейка, интерполяция,
преобразование чисел) идут в нашу кучу. Литералы хранятся в самом бинарнике.

Кодоген расставляет точки сборки после выражений, которые могут создать
управляемые значения, в том числе в условиях циклов. Есть два стека корней:

- `WIND_STR_ROOT` регистрирует адрес строковой переменной или параметра.
  Сборщик берёт её текущее значение, поэтому переприсваивание не держит
  старую строку живой. Запись удаляется при выходе из области видимости,
  в том числе при `return`, `break` и `continue`.
- `WIND_STR_EXPR` открывает временную область вычисления. Выделенные
  строки, прочитанные значения и результаты вызовов защищены до конца
  вычисления. Если один аргумент вычислен, а второй вызывает функцию,
  сборка в этой функции не удалит первый аргумент.

Оба стека находятся в `strings_gc.c`. Ссылки из списков, словарей и JSON
перечисляет их рантайм, а указатели в строковых массивах регистрируются
вместе. Перед `longjmp` WGC восстанавливает стеки до места `try`. Файловые
буферы и HTTP используют ту же кучу.

Поддержка произвольных нативных вызовов не входит в WGC: нет способа узнать,
сохранила ли чужая библиотека указатель на объект Wind. `link` передаёт
зависимость компоновщику, но не регистрирует такие ссылки. Ветка Windows
по-прежнему использует Boehm; она здесь не проверялась.
